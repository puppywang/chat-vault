# ChatGPT Sync 0.10.0 稳定性审查

范围：页面注入/失效生命周期、普通对话分轮计时、SSE/WS 测速、dots 状态标题、同步与回查、弹窗版本诊断。没有修改 ChatGPT 云端、Chappie 或 Pi，没有重启用户服务或刷新用户标签页。

## 根因与修复

| 优先级 | 发现 | 修复与验证 |
| --- | --- | --- |
| P1 | 重载扩展后旧页面仍存活，但 chrome API 已失效；后台版本不能代表页面版本 | `page-state.js` 统一生命周期，页面失效后停计时/观察器/测速并恢复原题名；弹窗同时显示两个版本和就绪状态 |
| P1 | 轮次结束后 await 再读当前路由，会把旧轮次写到新会话 | 回调携带并固定 path/用户消息 ID；迟到回查只属于原会话，延迟重画再次校验归属 |
| P1 | 多个标签页各自读改写 turnDurations，同步结束可能覆盖另一页记录 | 改为 service worker 串行写入，兼容原数据格式和原500条保留规则；并发和失败后恢复测试 |
| P1 | 显示、测速、注入开关没有统一生效点，部分后台循环继续工作 | 统一订阅状态；关显示只隐藏 UI，关注入停页面工作，网络 hook 透传；只取消扩展克隆流，不取消原请求 |
| P1 | dots 空闲文案存在 `Active 2分钟前`，不是单独的 Active | 以同名 dot 的隐藏空状态槽为必要证据；侧栏相对时间仅代表可用状态；真实工作文字、暂停、busy 不推断为空闲 |
| P2 | 重画、同步、恢复起点并发下载同一会话；测速失败连带阻止画徽标 | 在途请求复用；测速异常隔离；路由与绘制代际校验 |
| P2 | 计时宿主被 DOM 移除后仍持有旧引用；异步分词在关闭再开启后回写旧结果 | 宿主存活检查/重建；网络及分词使用采集代际隔离 |

## 为什么过去测试通过，页面仍有问题

旧测试主要覆盖单模块，并模拟选择器返回值。没有同时加载所有页面脚本验证真实 DOM/ShadowDOM、MutationObserver、动态开关及失效边界；用户重载后也缺少“页面代码实际版本”的验收。因此局部正确不能证明组合场景正常。

现在三层验证必须区分：

1. 单元/回归：请求归属、并发写入、设置加载竞态、异步取消、流回放。
2. 真实 Chrome DOM 集成：独立临时 profile、模拟 Chrome API/会话数据，同时加载实际页面脚本，验证计时恢复/推进/删除重建、开关、图片结束徽标、dots 工作→空闲、上下文失效；不是真实账号端到端验收。
3. 用户 profile 验收：通过扩展 CDP 只读读取实际 DOM/版本；新版本重载并刷新后，再验证真实一轮。只有这一步通过，才能宣称现场修复。

## 一键本地验证

```powershell
npm run verify:chatgpt
```

校验脚本语法和版本一致性，运行全部 `test/*.test.js`，再运行隔离 Chrome DOM 集成。Chrome 默认路径是 Windows 安装路径，可设置 `CHROME_PATH`。不会使用用户 profile、写真实归档数据库、自动重载扩展或部署。

## 上线验收

重载到 0.10.0 后，刷新需要使用的 ChatGPT 标签页；弹窗必须显示扩展和页面均为 0.10.0、已就绪。旧标签页显示无响应/旧版本时不能按新代码分析。

检查矩阵：普通对话发送→完成；完成后 F5；进行中 F5（缺少原始首段不补造 TTFT）；普通对话↔dots；dots 工作→空闲→暂停；两个会话同时结束；开关禁用再启用；扩展重载导致页面失效。

指标口径不变：SSE/WS 实际下发的助手文本分词；没有捕获到的内部输出不可测，dots 消息快照不可推算 token TPS。需要新增协议兼容时，先保留完整失败流，再离线回放、token 对账，不能用 DOM 估算掩盖采集缺口。

## 本轮现场证据

主 profile 同时存在响应的 0.9.8 dots 页和两个接收端不存在的旧页；其中一个旧页标题仍保留早期“状态未知＋最后消息”。因此仅看扩展后台版本会误判部署状态。

2026-09-30T16:40Z，通过扩展 CDP 只读观察到同名 dot 状态槽 `aria-hidden=true`、无 role/status 子内容，侧栏 `aria-busy=false`、文案 `Active 2分钟前`。已将这种真实形状加入单元和浏览器 DOM 测试。

本轮不把局部页面修复解释为历史所有卡死的唯一原因。长时间运行的 CPU/内存改善仍需同一对话、同等负载下的新旧版性能轨迹比较。

## 0.10.0 现场验收与 0.10.1 补充

用户重载并刷新后，两张页面都返回 `page_runtime.version=0.10.0`、`phase=ready`、无已记录错误；普通对话计时显示从57秒到1分00秒，dots显示 `[空闲] hot`。

续接边界尚有问题：2074 会话最后用户消息时间为 `2026-09-30T16:43:21.968Z`，页面 `performance.timeOrigin=1790786606257.7`（约16:43:26.258Z），计时却从 `1790786617195`（16:43:37.195Z）开始，晚约15.2秒。网络记录只有 init、会话读取、stream_status 和 `/backend-api/f/conversation/resume`，没有本页原始发送请求。

原因：历史分批渲染时，旧用户节点先出现，使 `primed=true`；当前轮次用户节点后出现，被误认为刚发送，跳过起点恢复。0.10.1 在已有会话请求返回时，按精确会话/用户消息 ID 校准正在计时的起点；已知发送早于本页加载/进入路由，且没有捕获原始请求时，将测速标为续接、显示“缺少原始起点”。不额外下载会话，不补造 TTFT/TPS。另将只读探针的停止按钮选择器与计时模块对齐，避免新版只有 `aria-label=停止` 时误报未回复。

新增 API先返回/DOM先出现、错消息/错会话、真正新发送、保留实际原始流的回归；Chrome集成另跑“先旧历史、后当前消息”的真实DOM时序。102项回归、两组各20项浏览器检查通过；仍需0.10.1刷新后的现场验收。

本地测试还发现服务端录制互斥检查未使用传入的临时诊断目录，会被用户真实CDP请求干扰；修正 `/stream/start` 的目录归属并增加隔离队列断言。未重启正在运行的ChatVault服务；该目录隔离改动不要求此次扩展用户重启服务。
